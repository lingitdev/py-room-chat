# Py-Room Chat Protocol (PRCP) Specification v1.0

## 1. Overview
Py-Room Chat Protocol (PRCP) is an application-layer communication protocol operating over raw TCP sockets. Packets are serialized as JSON objects and framed using a newline character (`\n`) (Line-delimited JSON).

---

## 2. Packet Framing & Transport
- **Transport Layer:** TCP / IP
- **Encoding:** UTF-8
- **Delimiter:** `\n` (Newline - Line-delimited JSON framing)

---

## 3. Data Packet Schema

Every data packet must strictly adhere to the following JSON structure:

| Field | Type | Required | Description |
| :--- | :--- | :--- | :--- |
| `msg-id` | String | Yes | Unique identifier assigned to the message (e.g., `msg-a1b2c3d4`). |
| `type` | String | Yes | Operation/action type identifier. |
| `to` | String | Yes | Intended recipient (`SRV`, `RM`, or `<nickname>`). |
| `fr` | String | Conditional | Sender identity. **Injected exclusively by the server.** |
| `pl` | String | Yes | Message payload / content. |
| `tm` | String | Yes | Timestamp (`YYYY-MM-DD HH:MM:SS`). |
| `v` | Float | Yes | Protocol version (default `1.0`). |

---

## 4. Message Types & Commands

### 4.1 Client Request Types
* `MSG`: Broadcast message to the room or send a direct message to a specific user.
* `CRT`: Request to create a new chat room.
* `JN`: Request to join an existing chat room.
* `JNMN`: Request to join the server's main lobby.
* `QT`: Request to leave the currently active chat room.
* `DISC`: Notification to terminate the connection session entirely.
* `PING`: Connection health check / heartbeat sent by the client.

### 4.2 Server Response Types
* `ACK`: Acknowledges that the requested operation was executed successfully.
* `ERR`: Signals an operational failure (includes an error code or description).
* `PONG`: Health check response sent in reply to a `PING` packet.
* `SYS`: System-wide announcements and event notifications (e.g., user connection status).

---

## 5. Protocol Rules & Constraints

1. **Client Header Restrictions:** Packets generated by clients **must never contain** the `fr` (from) field. The server validates client identity from its internal session state and injects this field into forwarded messages.
2. **Payload Routing Scope:** The `to` parameter is evaluated strictly for packets where `type: "MSG"`. For all other packet types, the recipient is implicitly treated as `SRV`.
3. **Join Request Formatting:** For `JN` and `JNMN` packet types, the `pl` (payload) field must be structured in the format `<room_id>@<room_pass>`.
4. **State Management:** Session states, such as authenticated client identities and current room affiliations, are maintained exclusively in server-side memory rather than being re-transmitted within packet headers.
